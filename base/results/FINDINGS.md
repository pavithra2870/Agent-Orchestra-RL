# Findings: Agentic Tool-Use Orchestration via Reinforcement Learning

Final cross-method comparison, generated by `evaluate_final.py` from each phase's
held-out evaluation episodes (300 per method; see `results/final/results_table.csv`
and `results/final/summary_grid.png`). All methods share the same environment,
reward formula (`success_reward - lambda*cost - mu*latency`, with a
`failure_penalty` on non-success terminals), and the same 10 task templates.

|---|---|---|---|---|---|---|---|
| rule_based | 1.000 | 8.20 | 5.67 | 5.38 | 0.962 | 0 (no training) | 0.546 |
| cql | 1.000 | 8.45 | 6.26 | 6.01 | 0.868 | 0 live episodes (offline) | 0.292 |
| sarsa | 0.963 | 7.69 | 5.96 | 5.85 | 0.920 | 3769 episodes | 1.056 |
| q_learning | 0.890 | 6.95 | 5.44 | 5.80 | 0.833 | 3862 episodes | 1.791 |
| dqn | 0.857 | 6.88 | 5.48 | 5.52 | 0.876 | 944 episodes | 1.862 |
| ppo | 0.800 | 6.59 | 2.98 | 3.07 | 0.901 | 9762 episodes | 2.147 |
| multi_agent | 0.797 | 6.27 | 3.42 | 3.45 | 0.947 | 10502 episodes | 2.327 |

## What worked

- **CQL is the headline result.** Trained on *zero* live environment episodes
  (purely on a 4000-episode logged dataset from a mix of the rule-based agent
  and a deliberately under-trained DQN), it matches rule-based's 100% success
  rate and achieves the *lowest* regret vs. oracle (0.29) of any method,
  including all the online ones. This is the offline-RL story working as
  intended: it isn't inventing better behavior than the data it saw, but
  Bellman backups let it recombine partial successes from both behavior
  policies into something that generalizes better than either one alone.
- **DQN is dramatically more sample-efficient than tabular Q-learning**
  (944 episodes to 80% success vs. 3862 for tabular Q-learning, ~4x faster)
  despite both learning the same value-based objective. The learned task
  embedding + generalization across similar states (rather than a
  from-scratch table entry per discretized state) is doing real work here --
  this is the clearest confirmation of Phase 2's premise, that function
  approximation should out-pace tabular methods as the state space grows.
- **The environment and reward formula are behaving as designed.** Regret vs.
  oracle increases monotonically as methods get "further" from either hand-
  coded knowledge (rule-based) or a strong offline dataset (CQL) toward
  harder online-exploration problems (PPO, multi-agent) -- exactly the
  ordering you'd expect, which is a useful sanity check that cost/latency/
  success are being measured consistently across every method.
- **The multi-agent delegation mechanic works end-to-end.** Independent PPO
  (triage + execution) converges cleanly to a stable ~80% success rate
  (see `results/phase4/plots/learning_curve_multi_agent.png`), and the
  triage agent learns to delegate selectively (0.77 delegations/episode,
  not on every step), i.e. it isn't defaulting to either "always delegate"
  or "never delegate."

## What didn't work / open questions

- **Tabular Q-learning and SARSA hadn't converged within their training
  budget** (see `results/phase1/plots/learning_curve_comparison.png`, still
  trending upward at episode 6000) -- and even so, neither one beat the
  hand-written rule-based heuristic on success rate (SARSA 96.3%, Q-learning
  89.0% vs. rule-based's 100%). Given the ~16,000-state discretized space
  used for tabular learning (documented in `src/utils/discretization.py`),
  this looks like a coverage problem, not a fundamentally bad policy -- more
  training episodes would likely close the gap further, but it also
  illustrates concretely *why* Phase 2 moves to function approximation.
- **Both PPO variants (single-agent and multi-agent) plateaued around
  80% success, converged, and stayed flat** (see their learning curves) --
  this is not an under-training artifact, it's a *found* policy. Both
  learned a genuinely different point on the cost/success tradeoff curve:
  much lower cost and latency (PPO: 2.98 & 3.07; multi-agent: 3.42 & 3.45,
  vs. 5.4-6.3 for the value-based methods), at the cost of roughly 15-20
  points of success rate. This is a legitimate Pareto tradeoff given
  `lambda`/`mu`, not obviously a bug -- but it does mean PPO here is
  optimizing successfully for a policy a stakeholder might *not* want
  (its regret vs. oracle, 2.15, is the second-worst of any method). A
  useful follow-up would be sweeping `ent_coef`/`clip_eps` or increasing
  `total_train_steps` to see whether PPO's plateau is a true local optimum
  or just needs longer training / different entropy regularization to keep
  exploring toward the higher-success region.
- **Multi-agent doesn't outperform its single-agent PPO counterpart** on any
  metric (797 vs 800 success rate, worse regret) -- delegation overhead
  (`DELEGATION_COST`/`DELEGATION_LATENCY`) is a pure tax in this task suite
  since no task *requires* two specialized skill sets simultaneously; the
  benefit of specialization here is mostly about which agent has cheaper
  *access* to which tools; a task suite with genuinely parallel subtasks
  (not explored in Phase 1's task templates) would be a fairer test of
  whether delegation helps.
- **"Held-out" caveat**: every method's final-eval episodes use a seed range
  disjoint from training, but all methods were trained and evaluated on the
  same fixed 10 task *templates* -- there is no true unseen-task-template
  holdout in this project. Regret/success-rate comparisons are therefore
  about policy quality *within* this task family, not out-of-distribution
  generalization to new task types.

## Ambiguities / decisions made along the way

See the individual `scripts/train_phaseN.py` scripts and the end-of-phase chat
summaries for the full list; the load-bearing ones for interpreting these
results:

- `failure_penalty` (default 2.0) was added to the reward beyond the
  base formula, to give agents a signal that *not*
  finishing is costly, not just neutral.
- Tabular RL's discretized state deliberately drops the "attempted" mask
  (keeps only "succeeded" mask + task id + budget/step bins) to keep the
  state space learnable; DQN/PPO/CQL all consume the full observation.
- The "richer state" in Phase 2 is a learned task embedding *inside* the
  network (`nn.Embedding` over task id), not a separate environment wrapper
  -- see `src/agents/dqn_agent.py` docstring.
- DQN/PPO were implemented from scratch in PyTorch rather than via
  stable-baselines3 (not installed in this environment, and a from-scratch
  implementation made the custom task-embedding architecture easier to share
  across DQN/PPO/CQL).
- Multi-agent execution's per-delegation decision is modeled as a
  single-shot contextual bandit (no bootstrapping) -- see
  `scripts/train_phase4.py` docstring for the reasoning.
- "Tool-call efficiency" = (minimum possible tool calls for the task) /
  (actual steps taken), averaged over successful episodes only.
- "Sample efficiency" = training episodes until an agent's rolling
  (window=100) success rate first reaches 80%; reported as 0 for
  rule-based (no training) and CQL (zero *live* episodes, though it does
  depend on a 4000-episode logged dataset generated by other policies).
