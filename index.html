The problem

Picking the next tool is the hard part.

AI agents work by calling tools: look up an order, check a policy, issue a refund. Today that choice is usually hard-coded as rules or left to a prompt.

That is hard to test, often wasteful, and risky when a tool moves money. I wanted to see if an agent could learn the right next step, finish the job cheaply, and never break a rule.

How it works

Read. Decide. Act. Check.

Every message runs through the same loop until the request is done or a human takes over.

Read

A language layer turns the message into goals. The policy never sees raw text.

Decide

The RL policy picks the next action. Anything not allowed right now is blocked before it chooses.

Act

The tool runs on a simulated shop with real business rules and random failures. What it learns feeds the next step.

Check

The reply uses only verified facts. A separate evaluator checks the final database, not what the agent says.

Delivery statusPayment changeRefund Cancel orderReturn or damage claimPolicy question

Six goals, any mix in one message. The agent learns the order of steps on its own.

Safety by design

Safety lives in the code, not in trust.

The policy can be wrong. The system around it is built so that being wrong never becomes unsafe.

The guardrail at work

Same DQN agent, with and without the action mask. Without it, the agent breaks rules in 16.6% of runs. With it, every agent breaks none.

Ask first

A yes before anything changes

Every refund, cancellation, payment change and return waits for the customer to confirm. If the customer is vague, the agent asks instead of guessing.

Input checks

Off-topic or unclear messages are caught before the agent acts.

Blocked actions

No refund without a passed check, no change to an order that is not verified.

Human hand-over

Big refunds, risky claims and tools that keep failing go to a person.

Lessons

Three things I got wrong.

The most useful parts of the project were the mistakes.

01

My perfect agent failed

I built an "oracle" that knows the hidden truth, so it should never fail. It solved only 85% of cases.

The bug was in my environment. It decided whether a question was needed based on what the agent had already looked up, not on the truth. After the fix, the oracle hit 100%.

Test the environment with an agent that cannot be wrong.
02

A default made a decision

A customer wrote "wanna pay now online itself". The agent changed their payment method even though nobody had picked UPI or card.

The environment was quietly filling in UPI when no method was given. Now the method has to come from the customer, and the change is blocked until it does.

Safety rules belong in the guardrail, not in defaults.
03

I used up my own test set

Adding returns and policy questions dropped the language layer from 90.8% to 79.6%. While fixing it, I read the test set's mistakes.

That meant it was no longer a fair test. I wrote a fresh one and reported only on that: 93.8%.

Once you read the test errors, it is not a test any more.

How it started

From a toy benchmark to a real use case.

It began as a small benchmark: ten made-up tasks and six mock tools, used to compare Q-learning, SARSA, DQN, PPO, offline CQL and a two-agent setup. Once that worked, I wanted something that felt real, so I rebuilt the same idea as a support agent for an online shop, with real business rules, safety checks and a live dashboard.

Where this fits

Built for agents that touch real things.

The same design works anywhere an agent calls tools that change something, and a wrong step costs money or trust.

Customer support

Refunds, returns, cancellations and order changes, with a human for the risky ones.

IT help desks

Password resets, access requests and ticket routing, without granting the wrong access.

Banking and payments

Disputes, card blocks and payment changes, where every action needs a check first.

Internal operations

HR, procurement and approvals, where steps follow rules and some need sign-off.

Honest limits

  • Everything is simulated, and the shop's rules are simple.
  • Three training seeds, so some results vary a lot.
  • Why PPO fails on unseen combinations is still untested.
  • The LLM tests used a small model on small samples.
